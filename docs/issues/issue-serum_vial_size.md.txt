# feat: Track nominal serum vial size (`serum_vial_size_mL`) on experimental conditions

**Type:** feat
**Area:** `database/models/conditions.py`
**Priority:** medium

---

## Problem

`ExperimentalConditions` (`database/models/conditions.py:6-92`) has no field for the size of the serum vial a Serum experiment runs in. Because there's no column, vial size can't be entered in the New Experiment wizard, the new-experiments bulk upload, or the Conditions tab edit modal. It also isn't available to Power BI. This issue is tracking only: no calculation reads the value. A later change may use it to compute headspace.

## Impact

Researchers can't record vial size or filter and group serum experiments by it in Power BI. When headspace calcs arrive, any serum experiment created before this lands will need a manual backfill, and every week without the field adds to that backlog.

## Fix

Add one nullable `Integer` column, `serum_vial_size_mL`, holding the **nominal** vial size in whole mL (20, 60, 120, 160, ...). The name follows the `water_volume_mL` convention (`conditions.py:27`), so raw SQL must quote it: `ec."serum_vial_size_mL"`. Existing rows stay NULL; no backfill.

Settled decisions:

- "Serum only" is enforced in the UI only. The API and bulk upload accept the field on any experiment type. Do **not** add a type check like `_validate_reactor_number` (`backend/api/routers/conditions.py:20-26`).
- Positive-integer validation lives in the API schema and the UI. No DB `CHECK` constraint (reason in Notes).
- The column goes into `v_experiment_conditions` only, not `v_experiments`.

### 1. Model (locked, additive)

Add after `water_volume_mL` (`database/models/conditions.py:27`):

    serum_vial_size_mL = Column(Integer, nullable=True)  # Nominal serum vial size, whole mL. Tracking only; no calc reads it yet.

`Integer` is already imported (line 1). No existing field, type, or relationship changes. This is the only change to a locked component, and this issue is the authorization for it.

### 2. Migration

Create a new revision off develop's head: `b8c4e2d7f9a1` as of `37ae701`, but confirm with `alembic heads`. Autogenerate adds the column; the view handling must be written by hand.

- `upgrade()`: `op.add_column("experimental_conditions", sa.Column("serum_vial_size_mL", sa.Integer(), nullable=True))`, then recreate `v_experiment_conditions` with the new column.
- `downgrade()`: recreate `v_experiment_conditions` with the **old** definition first, then `op.drop_column(...)`.

The order matters. `database/event_listeners.py:714-731` drops and recreates every view when the API imports. Once the service has started on the new code, the view depends on the column, and a plain `drop_column` downgrade fails with "cannot drop column ... because other objects depend on it." Follow the `_recreate()` helper and old/new SQL constants in `alembic/versions/c4d8f1a2b6e7_typed_notes_reporting_views.py:163-179`. Recreating the view in `upgrade()` also means Power BI sees the column right after the nightly `alembic upgrade head` (`update.ps1:228`), before the service restarts. No other view selects from `v_experiment_conditions`, so `CASCADE` drops nothing else.

## Notes

- **Nominal size, not true volume.** A "120 mL" serum vial holds noticeably more than 120 mL when filled to the brim. Headspace is total vial volume minus liquid volume, so the future calc will need the true total volume, either from a lookup by nominal size or from a measured column. State this in the MODELS.md entry so nobody later uses this column as the total volume.
- **Why no DB `CHECK (> 0)`.** The conditions-sheet loop (`new_experiments.py:864-1007`) has no per-row SAVEPOINT, unlike the experiments sheet (`:388`) and the additives sheet (`:1177`). A constraint violation would abort the transaction at the flush on line 954 and break every remaining row in the sheet. As specced, bulk upload doesn't validate this column, which matches how `reactor_number` behaves today. PostgreSQL silently rounds a fractional cell to an integer, and a non-numeric cell fails at flush and breaks the rest of the sheet the same way. That already applies to every numeric conditions column and is out of scope here.
- **Existing bug: the edit modal can't clear a field.** `set()` (`ConditionsTab.tsx:213-214`) turns an empty input into `undefined`. JSON serialization drops it, and `PATCH` uses `exclude_unset=True` (`routers/conditions.py:121`), so the old value survives. This affects the new field too: a mistaken vial size can't be removed from the UI. It deserves its own issue.
- Other code that loops over the model's columns picks up the new column with no change: `replicate_groups.py:50` (shared vs. divergent conditions in replicate groups), `experiment_deletion.py:213` (row snapshot), and `database/data_migrations/dedupe_conditions_and_backfill_ids_018.py:100`.
- Step 4 review labels each condition by its raw key (`Step4Review.tsx:63`), so this field appears as `serum_vial_size_mL`, like every other field there.
